- Миграция `20261006114105_reliability_concurrency_and_indexes.sql`: обща транзакционна ключалка по Stripe PaymentIntent за потвърждаване и възстановяване; индекси за чуждите ключове; изчистване на максимум 200 изтекли ограничения на заявка с `SKIP LOCKED`; обединени SELECT политики със запазени права.
- Входните тела имат предел в реални UTF-8 байтове и срок за прочитане. Невалиден JSON връща 400, прекалено голямо тяло — 413, блокирано четене — 408. Подписът на webhook се проверява върху непроменените байтове.
- Сървърните заявки към Supabase имат 10-секундно ограничение. Stripe заявките имат 10-секундно ограничение и най-много едно повторение. Запазени са ключовете за идемпотентност и отделянето на test/live режимите.
- Отказал ограничител или база връща безопасна грешка за повторение. При 429 се връща `Retry-After`. Лични текстове и сурови грешки от доставчици не се добавят в отговора.
- Четири неизползвани AI/телеметрични маршрута и празният `ping` връщат 410 без прочитане на тялото, запис или външен доставчик. Проверени са липсващите препратки към тях в текущия клиентски код.
- Sitemap чете публикуваните новини с публичен ключ и RLS, с ограничено време, кодирани сегменти на URL и 503 без кеширане при отказ на базата.
- Интерфейсът получава ограничени времена за заявките, обработка на грешки при новини с повторен опит и резервен екран при React грешка. Преходен отказ на базата вече не се записва като успешен празен списък в кеша.
- `tar` е фиксиран на 7.5.22, `postcss-selector-parser` — на 7.1.6. CSS след обновяването е идентичен байт по байт. CI проверява и критичните уязвимости в инструментите за разработка.

## Проверки на базата

- 500 повторения на вече обработено платежно събитие в управляваната база: 500 отчетени дубликата, един запис `payment_verified`, запазени 1499 платени и 1499 възстановени евроцента, статус `refunded/cancelled`.
- Изолиран ограничител с 24 опита и лимит 7: точно 7 допуснати и 17 отказани.
- Локален PostgreSQL тест с 1000 изтекли записа потвърждава ограничението от 200 изтривания и запазването на действащите ограничения.
- Опитите за застъпване на потвърждение и refund през управляващия SQL канал се изпълниха последователно, включително при задържане на транзакция 30 секунди. Те потвърждават крайното възстановяване, но **не доказват работа при две действително застъпващи се DB сесии**. PGlite също изпълнява редица заявки последователно. За тази отделна проверка е необходим тест с независими връзки в изолирана среда.
- Всички 19 приложни таблици са с включен RLS. Публичните заявки към частните таблици не върнаха данни. Автоматичните тестове покриват обикновен потребител, редактор, модератор, MFA администратор и отнемане на достъп.
- След тестовете: 10 връзки, една активна заявка, нула чакащи ключалки; база 14 797 971 байта, PostgreSQL 17.6. Това е моментна снимка, а не тест на максималния капацитет.
- Всички създадени за този пакет синтетични поръчки, токени, събития, истории и refund записи са изтрити с точни идентификатори. Съществуващите Stripe sandbox поръчки са запазени.

## Публикувано и оставащо

Миграцията е приложена в Supabase и сървърните функции са публикувани. Gateway настройките за JWT са запазени; чувствителните функции продължават да проверяват потребител, текущи права и MFA вътре в обработчика.

**Интерфейсът още трябва да се публикува през Readdy/текущия хостинг.** Репозиторият съдържа готовите промени и `vercel.json` за CSP, HSTS, забрана на рамки, `nosniff`, Referrer-Policy и Permissions-Policy. При последната HTTP проверка публичният хостинг не връща тези заглавки. Файлът ще действа само ако хостингът го прилага; наличието му в GitHub не е доказателство за активна защита.

Supabase Security Advisor продължава да показва **Leaked Password Protection Disabled**. Включването е настройка на Auth, която не е достъпна през използвания конектор: [инструкция за настройката](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection). Празните политики на частните таблици са умишлен отказ по подразбиране. Предупрежденията за липсващи FK индекси и дублирани SELECT политики са премахнати; неизползвани индекси не са изтривани само заради липса на статистика.

Дълъг тест с голям товар, независими PostgreSQL връзки и упражнение за възстановяване от backup не са извършени върху действащия проект. Не е правено обновяване или restore на PostgreSQL. Насоките за текущите [Supabase промени при PostgreSQL 17.11](https://supabase.com/changelog/postgres-15-19-17-11-breaking-changes) трябва да се вземат предвид при планирането на такова обновяване.

## Повторение

Използват се само публичните клиентски URL и ключ от локалната конфигурация; не се подават server keys. Сценариите са фиксирани към този проект и не приемат произволна цел.

```sh
npm ci
npm test
npm run typecheck
npm run check:edge
npm run build
npm audit --omit=dev --audit-level=high
npm audit --audit-level=critical
npm run stress:live -- after
npm run stress:live -- limits
```

`stress:live` записва само агрегати, статуси и безопасни описания на грешки; не записва тела на отговори, ключове, IP адреси или клиентски данни. Серията `limits` временно изчерпва минутния лимит за партньорския формуляр на адреса на тестовия клиент.
